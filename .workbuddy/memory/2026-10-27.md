## legado iOS 复刻 —— 打通构建链路

**背景**：上游 `HapeLee/legado-with-MD3`（Android/Kotlin），目标 iOS 原生复刻，
数据层与规则引擎一比一，UI 用 SwiftUI + 液态玻璃。上一阶段已铺了约 10.5k 行 Swift 骨架，
但从未编译通过（385 个错误）。

**依赖换源方案（本机关键约束）**：
- GitHub 直连约 30KB/s，git clone GRDB 十几分钟下不完。
- `xcodebuild` / `swift package` 编译 Package.swift 清单时 fork `sandbox-exec`，
  返回 `sandbox_apply: Operation not permitted`（外层已有沙箱，不允许嵌套）。
  但 `swift build --disable-sandbox` 正常。
- 最终方案：`scripts/fetch-vendor.sh` 从 `ghfast.top` 拉 tarball（带镜像回退列表）→
  `scripts/build-vendor-frameworks.sh` 用 swift build 交叉编译 device/sim-arm64/sim-x86_64
  三个切片、lipo 合并、手工组装 XCFramework → 主工程静态链接 `Vendor/Frameworks/*.xcframework`。
  首次全流程约 4 分钟，之后构建不入网。
- 宏插件同样被沙箱挡住，全域加 `-Xfrontend -disable-sandbox` 解决。
- GRDB 预编译成二进制后，主工程需显式暴露 `GRDBSQLite` 的 modulemap。

**编码踩坑**：
- 协议扩展里的成员不能充当另一个协议的 witness（`RuleJSONColumn` → `DatabaseValueConvertible` 会报
  "multiple matching properties"），必须给每个类型写显式扩展。
- 上游字段名 `init` 在 Swift 里改名 `initRule`，CodingKey 保留 `"init"`。

**结果**：`BUILD SUCCEEDED`，模拟器安装启动成功，书架页正常渲染。
两次提交：`f96d64e` 骨架、`59cab33` 构建链路 + 编译修复。

## P1/P2 推进（同一会话后续）

**数据层对齐**：写了脚本把上游 Kotlin `data class` 和本地 Swift struct 的字段名列表做 diff，
比人工核对可靠。查出三处偏差：ReviewRule 整组字段名是自造的（已按上游重写 10 个字段）；
BookGroup 缺 cover/bookSort/isPrivate；ReadRecord 表名与主键都不对（readRecords → readRecord，
主键改 (deviceId, bookName, bookAuthor)）。其余 BookSource/Book/BookChapter/SearchBook 全部一致。

**规则引擎测试**：从 0 补到 18 个。关键收获是测试真的抓到了 4 个会毁掉书源可用性的 bug：

1. `splitRegex` 用 `##` 之前的片段切片 —— `##正则##替换` 整段丢失，所有用 ## 的书源失效
2. `splitSourceRule` 里 `<js></js>` 的捕获组 2 未命中时用 NSNotFound 直接 substring → 必崩
3. `AnalyzeByJSoup` 括号索引 `[` 位置判断错位一位
4. `AnalyzeByJSONPath.getString` 多结果没按上游 `\n` 合并

**教训**：legado 规则的层级用 `@` 串联（`class.list@tag.span[1:2]@text`），
`.` 只是 `tag./class./id./text.` 前缀和旧式索引的分隔符；`div.span` 走 CSS 原义（class=span）。
我一开始按 CSS 直觉写测试，误判成引擎 bug，白折腾了一轮。

**环境**：GRDBSQLite 的 modulemap 和 `-disable-sandbox` 必须放工程级 settings，否则测试 target 链接不上。

结果：18 tests / 0 failures；模拟器重装后 DB 8 张表建表正常，schema 与 DDL 一致。

## 数据层完善（口径：书源解析 + DAO）

用户明确「数据层」包含书源解析，不只是 DB。参考了 LegadoTeam/legado 的测试目录——
那边多是「读源码断言 SQL 字符串」的契约测试，对 iOS 移植没直接价值；
本地上游 fork 的 45 个 data 测试（Room in-memory 行为测试）更有参考性。

**又修掉 3 个系统性 bug（都是测试逼出来的）**：

1. `Book.type` 是**位掩码**：上游 text=0b1000(8)、audio=32、image=64、webFile=128、
   local=256、notShelf=1024。本地写成了 0~4 枚举 → 书架类型筛选全废。
2. `RuleJSONCoding.encode` 用了 `JSONTool.stringify`，它走 JSONSerialization，
   对自定义 struct 退化成 Swift 调试字符串 → 所有书源的规则列落库后读回全 nil。
   必须用 JSONEncoder。
3. `SearchBook` 加了 infoHtml/tocHtml 运行期字段但没排除出 CodingKeys →
   insert 报「无该列」整条静默丢失。

**DAO 一律走 dbWrite 记日志**：原来满屏 `try?` 把约束/列名错误全吞了，
表现成「静默丢数据」，这是排查这类问题最费时的地方。

**解析层几个易错点（已验证与上游一致，别再"修"错）**：
- `chapterUrl` 规则**存相对路径**，读取时用 `BookChapter.getAbsoluteURL()` 补全
- 目录 `-` 前缀表示站点是倒序，会翻转；不加前缀时「先 reverse + 按 reverseToc reverse」两两抵消
- `formatJs` 需要绑定 `index`（1 基）、`chapter`、`title`，返回值直接覆盖标题

测试 18 → 55 全绿；SourceParseTests 用固定 HTML 脱网跑完整链路。

## P2/P3/P4 推进（对照官方 LegadoTeam/legado）

拉了官方源码到 `upstream-official/`（走 ghfast.top tarball，9.7MB / 9 秒；git clone 会很慢）。
官方与之前用的 fork 核心文件都有差异，主要是官方把 Rhino 换成了 htmlunit corejs、
新增 `mainJs`（纯 JS 单文件书源）、`BatchContentContext`、共享 JS 作用域等。
对 iOS 移植来说，规则语义基本一致，UI/引擎层差异不影响。

**本轮做的**：
- `Book.type` 之外的又一个大坑：HTTPClient 把整串 URL 跑 `addingPercentEncoding`，
  已编码的 `%E5` 会变成 `%25E5`。书源里带中文参数的地址基本都是已编码的，必然 404。
  改成「先屏蔽 % 再转义，最后还原」。
- 新增 `ConcurrentRateLimiter`（之前完全没有）：支持 `n/ms` 与单数字两种写法，
  按书源 key 全局共享，超限等待而非失败。
- `mainJs` 字段 + DB v2 迁移（用「列不存在才 add」写法，兼容全新安装与旧库升级）。
- AnalyzeUrl 接入限速与错误码分类（-1..-7，供调试页展示）。

**测试 55 → 81**，新增 NetworkTests（21 个）：URL 不二次编码、Set-Cookie 合并拆分
（`Expires` 里的逗号不能当分隔符）、Cookie 二级域名隔离 / 合并 / 4096 裁剪 /
会话与持久分层 / 冷启动复用、限速器额度与 key 隔离、AnalyzeUrl 编码与 option。
RuleEngineTests 补 `$n` 回填、`%%` 交叉合并、`@put` 标准 JSON、`@webjs` 分流。

**注意**：`chapterUrl` 存相对路径、目录 `-` 前缀翻转、`url` 保留原文而 `encodedQuery`
才是真正发出去的——这几个点验证过与上游一致，别按直觉"修"。

## 真实书源联网验证

从公开合集 `aoaostar/legado`（release 分支 sources/）拉到 6 个 JSON，解析出 22 个站点。
连通性：只有 6 个站点能直连（sudugu.co / dbxsd.com / shoujix.com / m.laikan9.com /
siluke.com / m.suixkan.com），其余 403（CF/反爬）或超时。

**结论：引擎没问题，公开书源规则大面积过期。**
- 速读谷：列表从 `class.bookbox` 改成了 `div.item.clear`，旧规则必然 0 结果
- 独步小说网（dedecms）：搜索接口直接返回「提示信息」页，不再返回列表
- 阅友小说：规则依赖 `@onclick` + JS 正则，站点也变了

按速读谷当前结构重写规则（`div.item.clear` / `#list li` / `div.con@html` /
`a:contains(下一页)@href`）后，真实站点上 **搜索 4 条 → 详情 → 目录 263 章 →
正文 1930 字（含 2 页分页）** 全通。

工程做法：`LiveSourceTests` 默认 skip（要 `TEST_RUNNER_RUN_LIVE_TESTS=1`），
硬断言只压在「手工校准」那条上，公开源作为信息性输出——免得源过期把 CI 弄红。
